# Scalable Market Basket Analysis Using Apache Spark FP-Growth

A B.Tech mini-project implementing a scalable market basket analysis
system that discovers frequently co-purchased product combinations
from retail transaction data using **Apache Spark MLlib's FP-Growth**
algorithm, with an interactive Streamlit dashboard for exploring
results.

---

## Project Overview

Retailers generate huge volumes of transaction data every day. Manually
spotting which products customers tend to buy together is impractical
at scale. This project builds an end-to-end, distributed data pipeline
that:

- Ingests and cleans large-scale retail transaction data using **Apache
  Spark DataFrames**.
- Mines **frequent itemsets** and **association rules** using Spark
  MLlib's distributed **FP-Growth** algorithm.
- Quantifies discovered relationships with **support, confidence, and
  lift**.
- Surfaces retailer-friendly **business insights** (cross-selling
  opportunities, strong associations, category relationships).
- Visualizes everything in an interactive **Streamlit dashboard**.
- Measures and documents **performance/scalability** across dataset
  sizes from 10,000 to 500,000 transactions.

## Dataset

A synthetic retail transaction dataset (`data/retail_transactions.csv`)
generated by `src/generate_dataset.py`, with one row per
(transaction, product) pair:

| Column | Description |
|---|---|
| transaction_id | Unique basket ID |
| customer_id | Unique customer ID |
| timestamp | Purchase date/time |
| product_id | Unique product ID |
| product_name | Product name (e.g. "Bread") |
| category | Product category (e.g. "Grocery") |
| quantity | Units purchased |
| price | Unit price |

Products span 6 categories (Grocery, Dairy, Beverages, Snacks, Personal
Care, Household) with ~30 total products. The generator seeds a small
set of realistic co-purchase tendencies (Bread→Butter, Pasta→Pasta
Sauce, Coffee→Sugar, etc.) so FP-Growth has genuine, non-trivial
patterns to rediscover — see `data/README.md` for details. The
dataset can be regenerated at any size:

```bash
python src/generate_dataset.py --num_transactions 100000
```

## Data Preprocessing

Implemented in `src/preprocess.py` using **Spark DataFrames** (the
big-data/distributed-processing requirement of this project — not
pandas):

1. Load CSV with schema inference and column validation.
2. Drop rows with missing/blank transaction IDs.
3. Drop rows with missing/blank product names.
4. Drop rows with invalid (≤ 0) quantities.
5. Drop rows with invalid (≤ 0) prices.
6. Drop duplicate (transaction_id, product_id) rows.
7. Aggregate into `transaction_id | items` (array of products per
   basket) — the input format Spark's FP-Growth requires.

---

## Why Spark?

Spark distributes DataFrame operations and the FP-Growth mining
algorithm itself across all available CPU cores (`local[*]` here,
trivially extendable to a real cluster by changing one config value).
This is what makes the pipeline genuinely **scalable** rather than
limited by a single Python thread and in-memory pandas DataFrame — see
`architecture.md` for a full explanation and diagram.

---

## FP-Growth Algorithm

We use **`pyspark.ml.fpm.FPGrowth`**, Spark MLlib's distributed
implementation of the FP-Growth (Frequent Pattern Growth) algorithm.
Unlike Apriori, FP-Growth avoids expensive candidate generation by
compressing the dataset into an FP-tree and mining it directly —
making it well suited to large transaction datasets.

Configurable parameters (`config/config.py`, or via CLI):
- `minSupport` (default `0.01`)
- `minConfidence` (default `0.2`)

---

## Association Rules

For every rule `[antecedent] → [consequent]` we report:

- **Support** — how frequently the item combination occurs across all
  transactions: `support(A∪B) = count(A∪B) / total_transactions`.
- **Confidence** — how often the consequent appears given the
  antecedent: `confidence(A→B) = support(A∪B) / support(A)`.
- **Lift** — how much more often A and B occur together than expected
  if they were independent: `lift(A→B) = confidence(A→B) / support(B)`.
  Lift > 1 indicates a genuine positive association.

The dashboard lets you filter rules by minimum support, confidence,
and lift, and explore them per-product rather than relying on a single
fixed "best products" ranking.

## Dashboard

`streamlit run dashboard/app.py` opens an interactive dashboard with:

- **Overview** metric cards (transactions, products, itemsets, rules)
- **Frequent Itemsets** table (sortable)
- **Association Rules** table with sidebar filters (min support /
  confidence / lift)
- **7 visualizations**: top products, top itemsets, support-vs-confidence
  scatter, confidence-vs-lift scatter, a NetworkX association network,
  a category-level relationship heatmap, and top cross-selling bars
- **Product Search** — pick any product and see its recommended
  pairings, generated dynamically from the actual rules
- **Business Insights** browser
- **Performance/Scalability** charts (once `performance_test.py` has
  been run)

The dashboard only reads files from `results/` — it never re-runs Spark
on its own, so it stays fast and responsive.

## Scalability

Because preprocessing and FP-Growth are both implemented with Spark
DataFrame/MLlib APIs (not pandas), the pipeline scales by:

- Increasing Spark parallelism (`local[*]` uses all CPU cores; a real
  deployment could point `SPARK_MASTER` at a multi-node cluster).
- Tuning `spark.sql.shuffle.partitions` for the dataset size.
- FP-Growth's FP-tree approach avoiding the combinatorial candidate
  explosion that plagues Apriori-style algorithms on large datasets.

See the Performance Analysis section/results for concrete, measured
numbers on this machine.

---

## Limitations

- Synthetic data is used since a real large-scale retailer transaction
  log was not available for this academic project; realistic
  co-purchase bias was seeded into the generator to keep results
  meaningful.
- Running on `local[*]` demonstrates Spark's parallel/distributed
  programming model but not true multi-node horizontal scaling — the
  same code would run on a real cluster with a config change only.
- FP-Growth's association network visualization only shows simple
  (single-item → single-item) rules for readability; multi-item rules
  are still available in the rules table.
